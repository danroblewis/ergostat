## 1. What the harness actually does, and why it is worth having

When a command fails inside a long session, its output (the exit code, the traceback, the last lines a test
printed, a git conflict listing) lands in the context window beside everything else the session holds: what it
just changed, what moved on main, which test failed under load yesterday, which subagent was slow last time,
what the owner said not to touch. The next token is generated with all of that in view, so the "retry" is never
the same input twice. Three things produce the behaviour:

- **The context holds the evidence and its neighbourhood.** The error is read against the recent diff and the
  known state, so the session can tell "my change broke it" from "it was already broken" from "the machine is
  busy".
- **Training gives a prior over failure modes.** A port in use, a stale lock file, a rate limit, a flaky
  browser wait, a hung merge, a missing import: the model has seen thousands, and recognises the class from a
  few lines of text. This is a fault library nobody wrote down.
- **The action space is open.** The session does not choose among pre-designed recoveries. It re-runs one test
  alone to classify it, checks `git status` instead of re-running a merge, kills the stuck process, resolves the
  conflict markers by hand, narrows the brief, or asks.

The Coordinator's part, as distinct from what any one worker does inside its own harness, is visible in last
night's log: two branches' agents stalled twice each, mid-step and uncommitted, and the coordinator noticed the
stall, read the worktrees, ran the suites, resolved the conflicts and merged by hand. It also noticed a pattern
across runs (a browser test that failed only under load) and fixed the test rather than retrying it. So the
Coordinator does four things a worker cannot do for itself:

1. **Detects** that a worker failed or, harder, that it stopped making progress while still alive.
2. **Salvages** partial work (the worktree, the half-built branch) rather than starting over.
3. **Classifies** the failure: transient, the item's own, the worker's brief, the environment, or a faulty
   measurement (the flaky test is a sensor fault, not a work fault).
4. **Escalates or generalises**: one bad item is set aside; many failures of one kind mean the system is wrong
   and something structural must change (the test, the timeout, the brief, the capacity).

The value is cost and honesty: blind repetition wastes money and can make things worse (a re-run merge on a
half-merged tree, duplicate work from a worker presumed dead), and an unclassified failure hides what the model
should learn.

## 2. Classical parallels, and where they fall short

- **Fault detection, isolation and recovery (FDI, FDIR; Isermann, Gertler).** Residuals are generated by
  comparing what a model predicts with what is measured; they are evaluated against thresholds (or CUSUM);
  faults are isolated by a *fault signature matrix* (each fault moves a known subset of residuals); recovery is
  *fault-tolerant control*, passive (a robust design that tolerates it) or active (reconfiguration to a
  pre-designed degraded mode). This is the closest frame. It falls short because the signature matrix and the
  reconfiguration modes are enumerated in advance; the harness isolates faults nobody listed, from free text,
  and invents the recovery.
- **Messaging reliability.** At-least-once delivery with *leases* (visibility timeouts, ack deadlines),
  renewal by heartbeat, ACK on success, redelivery on expiry, a delivery count, exponential *backoff* with
  jitter, a *dead-letter queue* for poison messages and a *redrive* from it. Robust and well understood; it
  only repeats. Diagnosis is left to whoever reads the DLQ.
- **Supervision trees (Erlang/OTP).** A supervisor restarts a failed child by a strategy, within a *maximum
  restart intensity* (so many restarts in so long); past it, the supervisor itself fails and its parent decides.
  This is escalation up a hierarchy, which maps directly onto ergostat's ladder. It restarts identically,
  assuming faults are transient.
- **Circuit breakers and bulkheads (Nygard).** Closed, open, half-open: stop calling what keeps failing, probe
  it after a cool-off. A gate that deactivates a loop, as 2.5's feedback asks for.
- **Statistical process control (Shewhart, Deming).** *Common-cause* variation (the system's own noise) versus
  *special-cause* (something assignable happened). Reacting to each common-cause failure as if it were special
  is *tampering* (the funnel experiment) and makes things worse; common causes are fixed by changing the system.
  This is the harness's "flaky or real?" question, and the Coordinator's "one bad item or a broken setup?"
- **The rework cycle (Cooper; Lyneis and Ford), in system dynamics.** Work done splits by an error fraction
  into work really done and *undiscovered rework*; checks discover it at a rate and send it back to work to do.
  It explains the failures found after an ACK (a claim contradicted, an intent verdict reopened), and why
  projects look on time until late. It is aggregate: it says how much, never why this one.
- **Watchdogs and jidoka.** A watchdog timer that must be kicked (liveness); stopping the line on a defect and
  asking why five times (Toyota).

None of these classifies an unforeseen fault from text and picks a new action. That narrow piece is what an AI
block supplies; everything around it (detection, counting, gating, escalation, setting aside, generalising) is
classical and belongs in the control structure.

## 3. What ergostat already has

- **Run outcomes, per block.** `agent.ran` / `agent.failed` with the exit code, the time taken and a note
  ("stopped after its timeout", "exited 2"), caused by `agent.started` (`ergostat/runner.py`); a machine block's
  `timeout` (SPEC §9.3); the status page says "its last run failed" and lists stale sensors
  (`ergostat/state.py`); `ergostat agents` shows the recent failures (`cli/agents.py`).
- **A lost run, detected late.** The session helper marks a session that never said how it ended as
  `session.lost` at the role's next run (`ergostat/session.py`, `lost()`): a lease expiry with no TTL.
- **Salvage, by hand in one example.** image-squeeze's `lab.py claim` resumes a hypothesis left in `building`
  with its worktree intact, and `abandon` drops one with a reason (`examples/image-squeeze/bin/lab.py`, flows
  `started`, `abandoned` in `lab.yaml`). This is checkpoint and restart, written per project.
- **Anti-windup.** A command that arrives while a block runs is held, not queued (§9.1): no pile of retries.
- **Detection after an ACK.** Claims checked against the record and the world, with trust measures and the
  `contradicted-claim` finding (§12g); the intent judge's verdicts and reopens (§12i). These are the discovery
  flow of the rework cycle.
- **A varied retry into a live session.** Messages delivered into a running `claude -p` session, or as the input
  of a resume (§12h): the channel for "your last attempt failed with X; do not repeat it".
- **Context recipes.** `item-history` and `state` parts, and per-recipe outcome measures,
  `ergostat.context.RECIPE.failed` (§12j): a sensor of systematic failure per kind of brief.
- **Alarms, counters, timers, compare, onoff** (§9.2), findings, "critical goal decaying" (§12), and the
  modelling loop (§12e) that turns findings and residuals into judged proposals.

What is missing, honestly:

- A failure is recorded **about the block, not the item** it worked on. The item stays in `building` forever
  unless the project's own script moves it. There is no attempt count, no lease, no return to the queue, no
  dead-letter state.
- **Liveness is not progress.** Nothing notices a run that is alive and silent (the stalled agents last night),
  although the run's transcript lines already arrive as events every two seconds and would serve as a heartbeat.
- **No classification**, so no difference between retrying, setting aside and stopping the line.
- **No breaker.** A block whose runs keep failing keeps being commanded.
- **No route from a pattern of failures to the modelling subsystem**, other than the generic residuals.

## 4. Candidate designs

### A. The lease queue with a dead-letter stock (the owner's sketch, made explicit)

Material layer: stocks `ready`, `leased`, `dead-lettered`, and the items' outcome; flows `leased` (ready to
leased: the worker's dequeue, its valve), `acked` (leased out to done), `expired` (leased back to ready, driven by
leases past their deadline), `nacked` (leased back to ready on a failed run), `dead-lettered` (leased to the DLQ
once attempts reach the most allowed), `redriven` (DLQ to ready), `discarded` (out of the DLQ). The lease,
deadline and attempt count are fields folded on the work item (`attempts: sum`, `lease_until: max`, the
evidence of each attempt `append`), so "done", "leased" and "dead" are the kind's projection of its fields, not
tasks. Renewal is any event caused by the worker's run (its transcript lines count): no new protocol.

Ladder: everything up to the DLQ is the rule rung (a small program shipped with the part). Diagnosis is a
block draining the DLQ, on whatever rung the project chooses.

Both views: SD sees an aging chain with a return loop and a sink, and Little's law gives time in the DLQ.
Control sees the worker as an actuator, the expiry as a watchdog, the DLQ goal as a balancing loop.

Weakness: it is diagnosis after N blind repeats, which is the opposite of what the harness does at attempt two.
And it sees one item at a time.

### B. Escalation up the ladder (supervision, with restart intensity)

Each failure moves the item one rung up a cascade of queues rather than back to the same one: first retry on the
same block with backoff (rule: transient faults); second, the same block resumed with the failure's evidence as a
message (§12h: the varied retry, cheap); third, a diagnoser on a higher rung (a stronger model, an agent with the
item history and the worktree); last, a person. A *restart intensity* per block (failures over a window, a
`counter` and `compare`) opens a breaker that stops commanding the block and raises the case one level up,
exactly as an OTP supervisor gives up and fails to its parent. Half-open: one probe run after a cool-off.

This is gain scheduling on the attempt count, and it gives parity with "vary, do not repeat" from the second
attempt. Weakness: escalation by count alone spends the expensive rungs on transient faults, and spends nothing on
the common cause.

### C. Classify first, then route (FDI with an open fault library)

A classifier sits on the failed edge, as the message classifier sits on the inbox (§12h): rules first (exit code,
timeout, lost, no progress, known text patterns), a narrow AI for the rest, an agent only for what neither places.
Its output is a route, not a diagnosis essay:

| Class | Route |
|---|---|
| transient (rate limit, busy machine, network) | back to `ready` after backoff; no attempt counted against the item |
| stalled (alive, no progress past the TTL) | salvage: lease returned with the workspace kept; the next attempt resumes |
| the item's own (cannot be built, contradicts a decision) | straight to the DLQ: do not burn retries on a poison item |
| the brief (context or instructions wrong, or too big) | re-brief: a patch to the item's hints, or a split |
| the environment or a common cause | breaker opens on the block; the case goes to the modelling subsystem |
| the measurement (a flaky test, a sensor that lies) | quarantine the check; a sensor fault for modelling, not a work fault |

The signature matrix is the residuals ergostat already computes: run outcomes, claims contradicted, intent
verdicts, stale sensors, fit residuals. The open part of the fault library lives in the classifier's prompt and
its accumulated corrections (2.13), not in code.

Weakness: the classifier is a new place for complexity to hide, unless its classes are flows (they should be: one
outflow per class, each counted).

### D. The rework cycle and a failure-rate control chart (the system view)

Treat failures as a rate with a mean and limits, per block and per class (a `counter` over a window, an `alarm`
at the control limit). Within the limits, failures are common cause: handled per item by A to C, and never
individually diagnosed by an expensive rung (no tampering). Past the limit, or on a run of points on one side,
it is a special cause on the system: the breaker opens and the modelling subsystem is given the neighbourhood.
Add the rework cycle's stocks for failures found after an ACK (`undiscovered-rework` drained by claims and the
intent judge into `known-rework`, back to `ready`), so the error fraction is a fitted parameter the model can
explain (by recipe, rung, item size).

This gives the Coordinator's "one bad item or a broken setup" judgement, and it is what makes failure data feed
the model. Alone it does nothing for a single item.

## 5. Recommendation

**C on the skeleton of A, with B's breaker and D's chart, shipped as a library part** (a parametric
"leased work queue" that any loop with items and machine blocks can instantiate), not a core item kind.

The reasons. A is the right material structure and the owner's instinct is sound: leases with renewal fix the
stalled-agent case, which was the one failure the coordinator actually spent last night on. But diagnosis must
come before the retries, not after them, or parity is lost at attempt two; so the classifier (C) sits on the
failed edge, cheap rungs first. The breaker (B) is the Coordinator's "stop launching into a broken setup", and
the chart (D) decides when one failure is a fact about the system; only then is the modelling subsystem called,
which keeps it from churning on noise. Every piece is a stock, a flow, a gate or a rule-rung block; the only AI
in it is the classifier's residue and the DLQ's diagnoser, each with a narrow output vocabulary.

```yaml
uses:                                  # a library part, instantiated with parameters (sketch)
  developer-queue:
    part: ergostat/leased-queue
    items: hypothesis                  # the work item kind it leases
    worker: block.developer
    lease: {ttl: 10m, renewed-by: run-events}   # any event the run causes; transcript lines count
    retry: {most: 3, backoff: [1m, 10m]}
    classify: block.failure-triage     # rules, then haiku; routes onto the flows below
    breaker: {failures: 4, within: 1h, cool-off: 30m}
    diagnose: block.dlq-diagnoser      # drains dead-lettered; context: diagnosis
# what it expands to, in the model's own terms:
#   stocks:  ready, leased, dead-lettered, undiscovered-rework
#   flows:   leased, acked, expired, nacked.{transient,brief,stalled}, dead-lettered, redriven, discarded, found-after-ack
#   goals:   dlq-young (oldest dead-lettered <= 1d), no-zombies (leased past ttl == 0)
#   blocks:  lease-keeper (program, rule rung), failure-triage, breaker (counter + compare gating the worker),
#            dlq-diagnoser (ai, outputs: redrive with hints, split, discard, correction.proposed, propose)
contexts:
  diagnosis:
    parts: [item-history, {state: {findings: true}}, {corrections: {kind: failures}}, model]
```

**The modelling subsystem's role.** It is the only thing that changes the TTL, retry limits, breaker thresholds,
the classifier's rules and the queue's structure, through proposals judged like any other (§12e). It is called
with a *neighbourhood*: the worker block, its queue, its sensors, its recipe and the goals they serve, plus the
failures by class over the window and the DLQ diagnoses with what eventually fixed each. On the rate of change:
a breaker opening pauses new leases, never a run in flight (a run already going is a trusted valve until its
lease ends or it fails); a changed parameter applies to the next lease, not the current one (bumpless transfer);
structural changes wait while the breaker is open, so the modeller is not changing the plant it is diagnosing.

**How we would know parity was reached** (scored on F3's transcript cases, plus the live demos):

- the share of retries that were blind (attempt n+1 given the same input as n, failing the same way): near 0;
- first-retry success after classification against retry-as-before;
- zombie leases (leased, no progress past TTL, not expired): 0; time from stall to detection under the TTL;
- for each failure the session hit (the stalled agents, the flaky browser test, the conflicts), whether the part
  chose the same class and recovery as the session did;
- breaker opens that a later diagnosis confirmed as common cause, against false opens;
- DLQ age, and diagnoses confirmed by what fixed the item.

**The old plan's Build.** Retract the `ergostat.failure` item kind: the failure is an attempt folded onto the
work item that already exists, and the DLQ is a state and a stock, not a kind. Retract the `diagnosis` output
line: the diagnoser's outputs are the ordinary vocabulary (patches to the item, `propose`, a correction
proposed, flows moved). Keep "diagnoses checked against what fixed it", as a measure. Change "a retry prompted to
diagnose first" into: the attempt's evidence on the item, read through the `item-history` part of the next
attempt's recipe, and delivered as a message when the session can be resumed.

From last night: **claims** and the **intent judge** are kept as the found-after-ACK flow of the rework cycle
(a contradicted claim is a nack after the fact); **messages** are the vehicle of the varied retry; **recipes**
supply the diagnosis context and their per-recipe failure measures feed the chart; **`session.lost`** should
become the generic lease expiry, detected at the TTL rather than at the next run; F2's roll-up must keep the
attempt fields (they are fold fields, so it does). Two small core needs follow: attributing a run's failure to
the item it was working on (§12h already infers which item a run works on), and a sensor measure of how long an
item has been quiet (since its last event from the worker), beside `measure: oldest`.

## 6. Open questions for the owner

- Should the leased queue be a maintained library part, or a starter set copied into a project's YAML?
- Is it acceptable that a transient failure does not count as an attempt against the item, so a long outage
  never dead-letters good work?
- When the breaker opens, should the modelling subsystem be woken at once, or only at its next scheduled pass?
- Should the DLQ diagnoser be allowed to redrive an item itself, or only propose a redrive for the owner?
- Is a flaky test a fault to quarantine automatically (the check unchecked, with why), or always a finding for
  you?
- Should stalls be judged by progress events alone, or should a worker be able to say it is busy and silent (a
  long build) to extend its lease?
